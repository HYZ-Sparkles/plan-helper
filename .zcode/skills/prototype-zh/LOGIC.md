# 逻辑原型

一个独立的、自包含的 HTML 文件（一个**可分享的 demo**），让任何人都能通过点击按钮驱动一个状态模型。**当问题是关于业务逻辑、状态转移或数据形态时**用它——这种问题在纸面上看着合理，但只有真把它推过几个 case，才能感觉到哪里不对。

因为是单文件、零安装，所以你能把它交给非开发者（设计师、PM、领域专家），让他们自己把玩模型。所以它说的是他们的语言，不是代码的语言。

## 何时这是对的形态

- "我不确定这个状态机能不能处理 X 然后 Y 这种边界 case。"
- "这个数据模型到底能不能表达……这种情况？"
- "我想在写之前，先把 API 该长什么样摸出来。"
- 任何有人想**按按钮、看状态变化**的场景。

如果问题是"这个该长什么样"，这条分支就错了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码之前，先把要原型的状态模型和要回答的问题写下来。一段话，放在 demo 顶部（可见的引言里，不只是注释）。一个回答错了问题的逻辑原型纯粹是浪费，所以把问题写明白，过后无论用户此刻在不在场、之后回来 AFK 都能核对。

### 2. 把逻辑隔离到一个可移植的模块里

把真正的逻辑（回答问题的那个东西）放到一个 `<script>` 块里，写成一个小而纯的模块——将来可以直接提出来、扔进真实代码库。它周围的页面是用完即弃的；这个模块不是。

形态取决于问题：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单值时合适。
- **状态机**：显式的状态与转移。当"当前状态下哪些动作合法"本身就是问题的一部分时合适。
- **一组纯函数**作用在一个普通数据类型上。没有隐含的当前状态、只有变换时合适。
- **一个有清晰方法面的类或模块**，当逻辑真的拥有持续的内部状态时合适。

选最贴合所问问题的形态，**不是**最方便接到页面上那种。保持纯粹：不碰 DOM、不碰 `document`、按钮处理器也不许钻进它内部。页面调用它，没有反向流动。这正是让原型在自身寿命之后还有用的原因：问题一旦回答，验证过的 reducer / 状态机 / 函数集就能完整地搬到真实模块里。

### 3. 搭出可分享的 HTML 文件

单文件，HTML/CSS/JS：不要框架、不要打包器、不要服务器，全部 inline，所以双击打开就行，发邮件也能跑。任何人打开就能用。

为非开发者写。每个 label 都用**领域语言**而非代码：按钮和状态读起来像业务语言，不像 reducer。用大白话解释正在发生什么。

按自顶向下的清晰层次排版：

1. **标题与一行解释**，说清这个 demo 让你探索什么（第 1 步的问题）。
2. **当前状态**：所有相关的完整状态，渲染为一个可读的 panel（带 label 的字段，不是一坨 JSON dump），每次点击后重渲染，让变化可见。在有助于非开发者跟随时，标出"刚变了什么"。
3. **自由点击按钮**：每个动作一个按钮，永远可用，让任何人都能按任意顺序戳模型。每次点击 dispatch 它的动作并重渲染状态。
4. **引导式走查**：一组**场景**，一个 tab 一个。每个 tab 里有一段场景的白话描述（设置的是什么情境、要观察什么），下面是这个场景要按的按钮顺序。每一步都是一个真按钮：点了就执行那个动作，进入下一步。启动一次走查会把状态重置到已知的初始状态，所以场景每次跑都一致。

选能展示那些纸面上难以推理的"尴尬 case"的场景：happy path、一个棘手的边界、一个本应被拒的尝试。

漂亮但克制：干净的字体、宽松的留白、一种强调色。不要动效、不要噱头：一切不与状态和按钮争夺注意力。

### 4. 交付

把文件发过去，或帮他们打开。他们有空时会在走查和自由点击里点来点去；有意思的时刻是他们说出"等下，那不应该可能"或"呃，我以为 X 会不一样"——那是**想法里的** bug，这正是整个原型的目的。他们想要新动作或新场景时，加上。原型是会演化的。

### 5. 沉淀答案和原型

原型回答了它的问题之后，按 [SKILL](SKILL.md) 描述的方式沉淀答案、再沉淀原型。逻辑分支的具体映射：验证过的 reducer / 状态机 / 函数集搬进真实模块（决策被吸收）；HTML shell 跟着去一次性分支，那分支把原型留作一手来源，因为它就是单文件，所以在那里始终能重新跑。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型。
- **不要接到真实数据库。** 用内存状态，除非问题专门是关于持久化的。
- **不要泛化。** 不要"将来万一要支持 X"。原型回答一个问题。
- **不要把逻辑和页面混在一起。** 纯模块一旦引用了 DOM、`document` 或按钮处理器，就搬不动了。让页面变成纯模块上的一层薄壳。
- **不要去抓框架、打包器、服务器。** 收件人双击就开的单文件；React app 或 dev server 把"可分享"给废了。
- **不要把 HTML shell 发到生产。** 页面是为手点优化的。它后面的逻辑模块才是值得留的。
