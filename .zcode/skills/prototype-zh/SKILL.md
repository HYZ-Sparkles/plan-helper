# 原型

原型是**用来回答一个问题的、用完即弃的代码**。问题决定形态。

## 选分支

依据用户的提示、上下文代码，或在用户在场时询问，来识别要回答的是哪个问题：

- **"这个逻辑 / 状态模型感觉对不对？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的单一 HTML 文件（自由点击按钮 + 带 tab 的引导式走查），把状态机推过那些纸面上难以推理的 case，并且让非开发者也能上手玩。
- **"这个该长什么样？"** → [UI.md](UI.md)。在同一条路由上生成几个**截然不同**的 UI 变体，通过 URL 查询参数和悬浮底栏切换。

两种分支产出截然不同的产物，所以选错就会浪费整个原型。若问题真的含糊、用户又联系不上，默认选与上下文代码最匹配的那一条（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部声明这个假设。

## 适用于两个分支的规则

1. **从第一天起就用完即弃，并明确标记。** 把原型代码放在它真正会被用到的地方附近（紧挨着它要原型的模块或页面），让上下文一目了然，但命名上要让随手翻的人一眼看出这是原型、不是生产代码。一次性 UI 路由要遵守项目已有的路由约定，不要自创新顶层结构。
2. **跑起来零门槛。** UI 原型以项目任务运行器的一条命令起步：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑 demo 是个双击就能开的 HTML 文件。总之，启动它不需要思考。
3. **默认不持久化。** 状态只在内存里。持久化是原型**要验证**的东西，不是它该依赖的东西。若问题明确涉及数据库，用一份 scratch DB 或本地文件，命名要清楚写上「PROTOTYPE, wipe me」。
4. **跳过打磨。** 不要测试、不要超出"能跑起来"的错误处理、不要抽象。重点是快速学到东西。
5. **让状态可见。** 每次动作（逻辑）或每次变体切换（UI）后，把所有相关的完整状态打印或渲染出来，让用户看到发生了什么变化。
6. **完成时沉淀下来。** 把验证过的决策折进真实代码，然后把原型本身作为**一手来源**沉淀下来：提交到一个一次性分支上（在 main 之外），并在实施 issue 上留一个指向该分支的上下文指针。答案（裁决和它定下来的问题）也记在 issue 或 commit 里。main 上只留下验证过的决策。
