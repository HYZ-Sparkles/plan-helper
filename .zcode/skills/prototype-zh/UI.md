# UI 原型

在同一条路由上生成**几个截然不同的 UI 变体**，从悬浮底栏切换。用户用浏览器翻一翻，挑一个（或从每个里偷一点），其余丢掉。

如果问题是关于逻辑/状态而不是"长什么样"，这条分支就错了。用 [LOGIC.md](LOGIC.md)。

## 何时这是对的形态

- "这个页面该长什么样？"
- "我想在拍板前看几个 dashboard 的备选。"
- "换个 settings 屏的布局试试。"
- 任何本来会让人花一天在脑子里比较三张模糊 mockup 的场景。

## 两种子形态：强烈倾向子形态 A

当 UI 原型**贴着实 app 长**时——真 header、真 sidebar、真数据、真密度——好判断得多。一个独立的一次性路由是个真空：每个变体孤立看都还行。只要附近有现成的页面能挂变体，默认走子形态 A。只有当原型真的无处可归时才用子形态 B。

### 子形态 A：调整已有页面（首选）

路由已存在。变体渲染在**同一条路由**上，用 `?variant=` URL 查询参数门控。已有的数据获取、params、auth 都不动，只换渲染部分。这是默认；除非有具体理由否则选它。

如果原型是为某个**还没**有页面、但*自然会落在某页面内*的东西（dashboard 的新 section、settings 屏的一张新卡、已有流程里的一步），它仍然是子形态 A。把变体挂进宿主页面里。

### 子形态 B：新页面（最后手段）

只有在被原型化的东西真的没有任何已有页面能住进去时（比如全新的顶层 surface，或一个无法合理嵌入任何地方的新流程）才用这个。

按项目已有的路由约定建一条**一次性路由**。不要自创新顶层结构。命名要让人一眼看出是原型（比如在路径或文件名里含 `prototype`）。同样用 `?variant=` 模式。

在承诺子形态 B 之前先 sanity-check：真的没有已有页面能嵌进去吗？空路由会掩盖设计问题，有人住的路由才能暴露。

两种子形态的悬浮底栏完全一样。

## 流程

### 1. 陈述问题并选 N

默认 **3 个变体**。超过 5 个就不再"截然不同"、开始变成噪音，所以封顶。

把方案落在一行，放在原型的位置或文件顶部注释里：

> "Settings 页的三个变体，通过 `?variant=` 切换，在已有的 `/settings` 路由上。"

不管用户在不在场想拍砖，这都管用。

### 2. 生成截然不同的变体

每个变体都按下面的标准做：

- 页面目的与它能拿到的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS，等等）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构性地不同**：不同的布局、不同的信息层次、不同的主要 affordance，不是只换颜色。三张略有不同的卡片网格不是 UI 原型，是墙纸。如果两份草稿太像，就按"不许用卡片网格"的明确指引重做一份。

### 3. 拼起来

在路由上做一个统一的切换器：

```tsx
// 伪代码，按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（已有页面）：切换器上方保留所有已有的数据获取；只有渲染的子树随变体换。

子形态 B（新页面）：`/prototype/<name>` 下的临时路由挂上同一个切换器。

### 4. 做悬浮切换器

屏幕底部居中的一个 fixed 定位小栏，三部分：

- **左箭头**：循环到上一个变体（绕回）。
- **变体 label**：显示当前变体 key，如果变体导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：循环到下一个（绕回）。

行为：

- 点箭头更新 URL 查询参数（用框架的 router，比如 Next 的 `router.replace`，React Router 的 `navigate`），让变体可分享、重载稳定。
- 键盘：`←` 和 `→` 箭头键也能循环。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时不要拦截方向键。
- 视觉上与页面区分开（比如高对比胶囊、轻投影），明显不"属于"被评估的设计。
- 生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价判断门控，让一次原型误合并也不会把栏发给用户。

把切换器放进一个共享组件，让两种子形态都能复用。放在项目里共享 UI 所在的位置。

### 5. 交付

把 URL（和 `?variant=` 的 key）摆出来。用户有空时会翻。真正有意思的反馈通常是**"我想要 B 的 header 加 C 的 sidebar"**——这才是他们真正想要的设计。

### 6. 沉淀答案并清理

变体胜出后，沉淀答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 描述的方式沉淀原型。把赢家折进真实代码，其余的挪到一次性分支，不要进 main：

- **子形态 A**：把赢家折进已有页面；从 main 里去掉落选的变体和切换器。
- **子形态 B**：把胜出的变体升级为真路由；从 main 里去掉临时路由和切换器。

完整的一套变体是一手来源，所以它落到一次性分支上、不是垃圾桶，因为变体组件和切换器留在 main 里会很快腐烂、迷惑下一个读者。

## 反模式

- **变体只在颜色或文案上不同。** 那是微调，不是原型。真正的变体要就结构打架。
- **变体间共用太多代码。** 共用一个 `<Header>` 没问题；共用 `<Layout>` 就废了初心。每个变体应该能自由扔掉布局。
- **把变体接到真 mutation。** 只读的原型就够了。若某个变体需要变更，指向一个 stub：问题是"该长什么样"，不是"后端通不通"。
- **直接把原型推到生产。** 变体代码是在原型约束下写的（没测试、最小错误处理）。折进来时按真代码重写一遍。
