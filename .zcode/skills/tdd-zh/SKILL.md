# 测试驱动开发

TDD 是红 → 绿循环。这个 skill 是让该循环产出**值得保留**的测试的参考：什么是好测试、测试放哪里、反模式、循环规则。每个章节在每次循环都适用——在循环前后查阅，不是循环之后。

探索代码库时，若 `CONTEXT.md` 存在就读它，让测试名和接口词汇对得上项目的领域语言，并尊重你所触及领域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，不验证实现细节。代码可以全变；测试不该变。一个好测试读起来像规范："user can checkout with valid cart" 让你一眼看到存在什么能力，并且因为不关心内部结构，重构时活下来。

看 [tests.md](tests.md) 里的示例和 [mocking.md](mocking.md) 里的 mock 准则。

## 接缝：测试放在哪里

**接缝**是你测试所在的公共边界——无需钻进内部就能观察行为的接口。测试活在接缝上，永远不针对内部。

**只在事先约定的接缝上测试。** 在写任何测试之前，先写下要测的接缝并和用户确认。没有任何测试写在未经确认的接缝上。你不能测一切，所以事先约定接缝就是让测试力量落在关键路径和复杂逻辑上，而不是每个边角。

问："公共接口是什么？我们应该测哪些接缝？"

当那个接口的形状本身就在被讨论（模块多深、接缝该在哪、接口应该暴露什么）时，调 Skill 工具传 "codebase-design" 拿术语词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共享源头，是参考不是会话。

## 反模式

- **实现耦合**：mock 内部协作者、测私有方法、或通过侧信道验证（绕过接口查数据库）。特征：重构没改行为时测试就破。
- **重言式**：断言按代码的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、按同样方式手算的 snapshot、断言等于自身的常量），所以通过是构造出来的，永远不会与代码不一致。期望值必须来自独立的事实之源：已知的字面量、演算过的例子、spec。
- **横向切片**：先写完所有测试、再写所有实现。批量测试验证的是**想象出的**行为：你测的是**形状**而不是用户面对的行为；测试对真实变化变得不敏感；你在还没理解实现时就承诺了测试结构。改为**纵向切片**工作：一个测试 → 一份实现 → 重复，每个测试都是响应上一次循环所教你的**示踪子弹**。

## 循环的规则

- **红先于绿。** 先写失败的测试，再写刚好够让它通过的代码。不要预见未来的测试或加投机性的功能。
- **一次一片。** 一个接缝、一个测试、一份最小实现，每个循环。
- **重构不属于循环。** 它属于 review 阶段（见 `code-review` skill），不属于红 → 绿实现循环。
